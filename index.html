2. 프로세스 상태 전이도 & 프로세스 생성

  • New: fork() 호출로 프로세스가 생성된 직후
  • Ready: CPU 할당받으면 바로 실행가능. 메모리 적재됨
  • Running: CPU 점유하여 명령어 수행중인 상태
  • Waiting / Blocked: I/O 작업 끝나길 기다림
  • Terminated: 실행 끝
  • 좀비 프로세스: 자식 종료됨. 부모 확인안해 남아있음
  • 고아 프로세스: 자식 실행중. 부모 먼저 종료됨

프로세스 생성 수식 (fork)

• 전체 프로세스 (부모포함): 2n
• 새로 생성된 자식 프로세스: 2n - 1

3. CPU 스케줄링 & 성능 지표

선점 스케줄링 조건 (문맥교환 발생 4가지):
1. 실행 → 블록 (Running → Blocked)
2. 실행 → 준비 (Running → Ready)
3. 블록 → 준비 (Blocked → Ready)
4. 새로운 프로세스 선택 시
  • 디스패처: 문맥교환을 수행하는 모듈
  • 처리량: 단위시간당 완료된 프로세스 개수

스케줄링 알고리즘 분류

분류 알고리즘 원문 특징 및 처리 방식
선점형 RR, SRT 선점 가능
비선점형 FCFS, SJF, HRRN 비선점 (완료 시까지 CPU 점유)
우선순위 우선순위 스케줄링 기아현상 발생 가능 → 노화(Aging) 사용하여 해결

시간 및 성능 지표 계산 공식

• CPU 이용률 = 전체사용시간 - 오버헤드 CPU 전체 사용시간

• 총체류시간: 완료시간 - 도착시간
• 반환시간: 완료시간 - 도착시간
• 대기시간: CPU 할당 대기
  → 대기시간 = 반환시간 - 도착시간 - 실행시간
• 응답시간: 첫 응답 나오기까지 시간 (CPU 차지하는데 걸린시간)

• HRRN 우선순위 = 대기시간 + 서비스시간 서비스시간 = 1 + 대기시간 서비스시간

• EDF: 마감시간이 빠를수록 우선순위 높아짐. 주기단위 1회 실행

4. 동기화 (Synchronization) & 스케줄링 조건

실행 / 준비 파라미터에 따른 방식 판별

조건식 (파라미터 부등식) 필기 예시 수치 결정되는 방식
실행(β) > 준비(α) > 0 β=2, α=1 FCFS
준비(α) < 실행(β) < 0 α=-2, β=-4 LIFO
준비(α) > 실행(β) > 0 α=2, β=1 RR

임계구역 3대 조건

  • 상호배제: 동시에 CS 진입 ✕
  • 진행: CS 비어있다면 → 나도 너도 못들어가 (✕, 비어있으면 누구든 들어가야 함)
  • 한계대기: HW 문제 → 나만 못들어감 (✕, 유한한 대기시간 보장 필요)

Mutex & Semaphore

  • Mutex Locks: 상호배제
  • Semaphore: 자원의 갯수를 관리
    • 양수: CS에 진입 가능한 프로세스의 수
    • 음수: CS에 진입을 기다리는 프로세스의 수
    • 카운팅세마포: 주차공간 10개
    • 이진세마포: 1명만 가는 화장실
    • 세마포 문제점: 배치가 잘못되면 교착 발생

5. 교착상태 (Deadlock) & 은행원 알고리즘

교착상태 4가지 필요조건

조건명 원문 기재 의미 보충 설명
상호배제 자원공유 ✕ 한 번에 한 프로세스만 사용 가능
점유 & 대기 갖고 요청 자원을 보유한 채 다른 자원 요구
비선점 빼앗음 ✕ 강제로 회수할 수 없음
순환대기 원형싸이클 프로세스 간 원형 대기 체인 형성
  • 요청: P → R (프로세스가 자원을 요청)
  • 할당: R → P (자원이 프로세스에 할당)

은행원 알고리즘 수식

• 요청 시 자원 변동:
  Available = Available - Request
  Allocation = Allocation + Request
  Need = Need - Request

• 총 자원 관계식:
  총자원 = Allocation + Available
교착상태 알고리즘:
Max 가 없음 (은행원 알고리즘과 달리 최대 요구량 Max에 대한 정보 없이 현재 할당/요청 정보로 검출 진행).

6. 트랜잭션 회복 기법: 즉시 갱신 vs 지연 갱신

로그 기반 회복 기법(Log-Based Recovery)은 시스템 장애 발생 시 로그 파일에 기록된 내용을 바탕으로 데이터의 일관성을 회복하는 핵심 메커니즘입니다.

즉시 갱신 vs 지연 갱신 핵심 비교

비교 항목 즉시 갱신 기법 (Immediate Modification) 지연 갱신 기법 (Deferred Modification)
DB 실제 반영 시점 트랜잭션 실행 중 연산이 발생할 때마다 즉시 실제 DB에 기록 트랜잭션이 부분 완료(Commit)될 때까지 DB 반영을 지연하고 로그에만 기록
로그 기록 내용 이전 값(Old Value)과 변경된 값(New Value) 모두 기록
형식: <T, X, Vold, Vnew>		 변경된 새 값(New Value)만 기록
형식: <T, X, Vnew>
회복 시 수행 연산 REDO 및 UNDO 모두 수행 가능 REDO만 수행 (UNDO는 필요 없음)
UNDO가 필요 없는 이유 실행 도중 DB에 이미 변경 데이터가 반영되었으므로 장애 시 이전 값으로 되돌려야 함(UNDO 필수) Commit 이전에는 실제 DB에 아무것도 반영하지 않았으므로, 변경 사항을 취소할 작업 자체가 없음

장애 발생 시 REDO / UNDO 판별 규칙 (시험 빈출)

1. 로그에 <Start>와 <Commit>(또는 Checkpoint)이 모두 있는 경우:
  → 정상 완료된 트랜잭션이므로 장애 시 재실행하여 반영 보장: REDO 수행

2. 로그에 <Start>만 있고 <Commit> 기록이 없는 경우:
  • 즉시 갱신 기법: DB에 미완료 데이터가 쓰였으므로 취소 작업 필수: UNDO 수행
  • 지연 갱신 기법: 실제 DB에 쓴 적이 없으므로 해당 로그 무시: 아무 작업도 안 함 (UNDO 생략)
⚠️ 시험장 직전 체크 포인트
• 문제에서 "UNDO 작업이 전혀 필요 없는 회복 기법은?"이라고 묻는다면 정답은 무조건 지연 갱신(Deferred Modification)입니다.
• 체크포인트(검사점, Checkpoint) 기법이 함께 적용된 경우: 체크포인트 이전에 이미 완료(Commit)된 트랜잭션은 회복 대상에서 완전히 제외되어 REDO/UNDO 대상 목록 계산 시간을 대폭 줄여줍니다.
